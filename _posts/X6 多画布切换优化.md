# 一、先确认你的实现方式（非常关键）

你现在切换 Tab 时，大概率是：

- 销毁旧 Graph

如果是这样，卡顿是必然的。

# 二、正确的多画布设计思路

你要的不是“重绘”，而是：

> ✅ 画布实例只创建一次  
> ✅ 切换时只做显示/隐藏  
> ❗ 不重新渲染

---

# 三、推荐三种优化方案（按推荐程度排序）

---

# ✅ 方案一（最推荐）：Graph 实例缓存 + DOM 显隐切换

## 原理

- 每个 Tab 对应一个 Graph 实例
- Graph 只初始化一次
- 切换时只切换 container 显隐
- 不销毁，不重新 loadData

---

## 示例结构

```html
<el-tabs v-model="activeTab">
  <el-tab-pane
    v-for="tab in tabs"
    :key="tab.id"
    :name="tab.id"
  >
    <div
      :ref="el => setContainerRef(tab.id, el)"
      class="graph-container"
      v-show="activeTab === tab.id"
    ></div>
  </el-tab-pane>
</el-tabs>
```

---

## graph 缓存

```js
import { Graph } from '@antv/x6'

const graphMap = new Map()

function initGraph(id, container) {
  if (graphMap.has(id)) return

  const graph = new Graph({
    container,
    grid: true,
    async: true,   // 非常重要
    interacting: false, // 如果不需要频繁交互
  })

  graphMap.set(id, graph)
}
```

---

## 切换时

```js
watch(activeTab, (val) => {
  nextTick(() => {
    const graph = graphMap.get(val)
    if (graph) {
      graph.resize()
    }
  })
})
```

---

## 为什么 resize 必须？

因为 X6 在隐藏 DOM 时会计算错误宽高。

# 一、核心优化思路

你现在卡顿的根源不是 clearCells。

而是：

> 每添加一个 node/edge，X6 都在实时渲染

也就是：

```
addNode() -> 渲染

addEdge() -> 渲染
```

这是 N 次渲染。

---

# ✅ 最重要优化（立刻有效）

# 使用 freeze + batchUpdate

在清空和重建期间冻结渲染。

---

## 改造前

```js
graph.clearCells()

nodes.forEach(node => {
  graph.addNode(node)
})

edges.forEach(edge => {
  graph.addEdge(edge)
})
```

---

## 改造后（强烈推荐）

```js
graph.freeze()

graph.batchUpdate(() => {
  graph.clearCells()

  nodes.forEach(node => {
    graph.addNode(node)
  })

  edges.forEach(edge => {
    graph.addEdge(edge)
  })
})

graph.unfreeze()
```

---

# 🔥 原理

- freeze() 阻止 DOM 更新
- batchUpdate() 合并变更
- unfreeze() 一次性渲染

从：

> N 次 DOM 重排

变成：

> 1 次 DOM 更新

性能差距非常大。

# chatgpt response

很好，这个问题问得非常关键 👍  
在 **X6 1.x** 里，`startBatch / stopBatch` 和 `freeze / unfreeze` 是两套完全不同的机制，很多人会混淆。

---

# 一、先说结论

> 🔹 `stopBatch` 不负责“性能优化”  
> 🔹 它的核心作用是“合并事件和历史记录”  
> 🔹 它 ≠ 暂停渲染  

如果你是为了解决切换 Tab 卡顿问题：

👉 **stopBatch 基本没什么帮助**

---

# 二、stopBatch 到底是干什么的？

它配套的是：

```js
graph.startBatch('name')
graph.stopBatch('name')
```

---

## 它的作用是：

### 1️⃣ 合并 history 记录

如果开启了 history：

```js
graph.startBatch('update')

graph.addNode(...)
graph.addEdge(...)
graph.removeCell(...)

graph.stopBatch('update')
```

那么：

> 这一堆操作会被视为一次 undo

否则每个操作都会生成一条 history。

---

### 2️⃣ 合并事件触发

在 batch 期间：

- 不会频繁触发 change 事件
- stopBatch 时统一触发

---

# 三、stopBatch 不会做什么？

它不会：

❌ 暂停 DOM 渲染  
❌ 阻止浏览器重排  
❌ 合并绘制  
❌ 冻结 graph  

也就是说：

```
addNode
addNode
addNode
```

即使在 startBatch 里，

DOM 仍然会一条条创建。

---

# 四、真正影响渲染性能的是

在 1.x 里：

```
graph.freeze()
graph.unfreeze()
```

这才是：

> 暂停渲染 → 批量执行 → 一次性渲染

---

# 五、三者区别对比

| 方法 | 是否暂停渲染 | 是否合并历史 | 是否减少DOM更新 |
|-------|-------------|--------------|----------------|
| startBatch | ❌ | ✅ | ❌ |
| stopBatch | ❌ | ✅ | ❌ |
| freeze | ✅ | ❌ | ✅ |
| resetCells | 内部批处理 | - | ✅ |

---

# 六、为什么很多人以为 stopBatch 能优化性能？

因为：

- stopBatch 减少了 change 事件
- history 合并后 CPU 下降

但：

> DOM 创建成本仍然存在

如果你节点多（几百上千）：

stopBatch 几乎没用。

---

# 七、你现在的情况

你：

> clearCells → addNode → addEdge  
> 使用 stopBatch  
> 仍然卡

这是正常的。

因为：

你只是合并了 history，  
但没有减少 DOM 创建。

# 八、正确组合方式（X6 1.x 推荐）

如果你既要：

- 合并历史
- 又要优化性能

graph.freeze()

graph.resetCells([
  ...nodes,
